# 开发故事：一个想法，和一次 AI 的完整工程实现

## 起因

项目发起人（下称“用户”）有一批 3D 打印件，总是从层间裂开。FDM 打印的水平强度通常够用，**真正薄弱的是 Z 轴**：同一位置逐层堆叠的墙，缝与缝完全对齐。

用户最早的诉求很朴素：*“能不能让内墙像砌砖一样，上下层错开半个线宽？”*

## 第一轮尝试：G-code 后处理

最初的方案是社区现成的脚本（bricklayers 类）：切片完成后改 G-code，把内层墙抬高半层。
实测发现问题：**它在 XY 平面上完全没动**——提取相邻两层的内墙坐标一比对，位置完全重合，只是 Z 变了。这不能形成真正的咬合。

## 第二轮尝试：在 G-code 里横向偏移

于是尝试直接改 G-code 的 X/Y：把内墙沿法线偏移半个线宽。
结果更糟：

- 切片器输出的“一圈墙”在 G-code 里被拆成多段**开口折线**，起点终点不闭合，法线算不准；
- 强行闭合再偏移，会把圆环结构带歪，出现空隙和错位；
- 斜面上还会出现悬空和内墙外凸。

结论：**G-code 层面拿不到“第几圈墙”的语义，这条路走不通。**

## 第三轮尝试：进入切片器内部

于是转向修改 OrcaSlicer 源码（基于社区的 staggered perimeters 分支）：

- 先做“整圈多边形 offset(±w/2)”；
- 内墙终于动了，但圆环结构上会**少一圈、留空隙**，斜面上也不理想；
- 又试了“隔层双倍线宽、留缝再补”，逻辑复杂、外观不可控。

两次都不满意。

## 转折：用户的一个洞察

用户提出：

> 不要动路径。**只把首圈（外墙）的线宽改成一半**——外墙中心线会跟着往里挪，外表面仍然贴着模型；
> 而第一圈内墙的位置是由“外墙宽 + 内墙宽”推出来的，所以**整组内墙会自然向外平移半个线宽**。

这是一个非常漂亮的几何观察。AI 立刻做了推导验证：

```
ring0 = B − w₀/2                        （外表面 = B，永远齐平）
ring1 = B − (2·w₀ + w₁)/2               （w₀ 变，ring1 平移 Δw₀/2）
ring2..n = ring1 − perimeter_spacing    （整组跟随）
```

结论：**只改一个 flow 宽度，就能让整组墙平移，且不产生重叠或空隙。**
不需要 offset、不需要额外路径、不需要处理拓扑。

## 实现与验证

AI 负责了全部工程工作：

1. 阅读 OrcaSlicer 源码，定位到 `PerimeterGenerator::process_classic/process_arachne`；
2. 新增配置项 `brick_wall_mode`（无 / 半宽交替 / 宽窄交替），接入 GUI（工艺 → 强度 → 墙）；
3. 实现 `apply_brick_outer_width()`：按层覆写 `ext_perimeter_flow` 的线宽；
4. 从零搭建编译环境（VS 2022 Build Tools、CMake、Strawberry Perl、依赖代理、长路径支持等）；
5. 处理编译错误（枚举静态映射、重复定义、函数签名等）；
6. 编译出定制版 OrcaSlicer，并确认选项进入界面。

用户负责：提出思路、判断方向、实际切片验证。
最终效果：相邻层内墙错开半个线宽，上下咬合，外表面保持齐平——**符合预期**。

## 关于“AI 写的”

这个项目的代码几乎全部由 AI 编写：分析、设计、实现、编译、排错、文档。
用户提供的是**问题、直觉和判断**——尤其是“只改首圈线宽”这个关键洞察，直接决定了最终方案的简洁程度。

我们认为这是一次有意义的人机协作：人负责想，AI 负责把它变成能跑的东西。

## 为什么开源

用户认为这个算法不值得、也不应该被商业化垄断：

- 它足够简单，简单到“说破之后人人都能实现”；
- 它对普通打印者的价值远大于对任何公司的价值；
- 砖砌层方向本身已有专利争议，公开出来可以**作为现有技术，阻止后来者圈地**。

因此：**免费开源，允许商业使用；但任何组织或个人不得就本算法申请专利牟利或垄断。**
